跨时间域生物面部识别系统——后端系统实现

说明：
本章节按后端包结构展开，先给出大类（common、config、dto、entity、mapper、controller、service），再在每个包内按照具体类讲实现逻辑、关键代码、调用链路和设计原因。文本已融合你提供的说明内容，并在原有结构内补充必要细节；不采用“在文末额外追加”方式。

======================================================================
第一章 系统整体实现思路与架构落地
======================================================================

本后端系统要解决的核心问题不是“单次调算法拿结果”，而是“把识别过程工程化”：
1）上传图片后，能够被稳定保存；
2）调用算法后，无论成功失败都要可追踪；
3）能从任务视角查询，也能从个体视角回溯；
4）能回答“谁在什么时候上传了哪张图”；
5）前后端联调时，接口风格统一、错误返回统一；
6）与 Python 算法协作时，协议边界清晰、改动成本低。

系统采用 Spring Boot + MyBatis + MySQL + WebClient，分层如下：
（1）controller：接口协议入口；
（2）service：业务编排核心；
（3）mapper：SQL 访问层；
（4）entity：表结构映射；
（5）dto：对外传输模型；
（6）common：统一响应 + 全局异常；
（7）config：全局配置 + 认证过滤。

典型主链路：
前端上传 -> AuthFilter 解析登录态 -> RecognitionController.upload -> RecognitionService.submit ->
保存文件 + 识别记录落库 processing -> AlgorithmClientService 调 Python ->
成功则 done + 归并个体，失败则 failed -> Result 返回前端。

这条链路体现了“流程先可追踪，结果再可展示”的工程思路。

======================================================================
第二章 common 包实现
======================================================================

common 包的定位是“协议标准化”和“异常治理标准化”，不承载具体业务计算。

----------------------------------------------------------------------
2.1 Result：统一接口响应协议
----------------------------------------------------------------------

Result 结构为 code/message/data，是全系统对前端的统一返回契约。  
为什么必须统一：
1）前端只写一套响应处理逻辑；
2）错误分支统一，不会出现有的接口返回字符串、有的返回对象；
3）日志与排障可以统一按 code 分析。

当前实现方法：
1）ok(data)：成功并带数据；
2）ok()：成功无数据；
3）fail(ResultCode)：失败默认文案；
4）fail(ResultCode, message)：失败自定义文案；
5）fail(int, message)：兼容旧写法。

使用统一 Result 的直接收益是：Controller 几乎不用手写 JSON 协议，接口风格稳定。

----------------------------------------------------------------------
2.2 ResultCode：语义化状态码
----------------------------------------------------------------------

ResultCode 枚举已覆盖常见状态：
OK、BAD_REQUEST、UNAUTHORIZED、NOT_FOUND、CONFLICT、SERVER_ERROR、BAD_GATEWAY。

语义化后好处非常明显：
`Result.fail(ResultCode.UNAUTHORIZED, "未登录")`
比
`Result.fail(401, "未登录")`
更可读、更好维护。

这也是你在代码里将“魔法数字”替换掉的主要价值：不是语法变化，而是协作可读性提升。

----------------------------------------------------------------------
2.3 GlobalExceptionHandler：异常统一出口
----------------------------------------------------------------------

该类通过 `@RestControllerAdvice` + `@ExceptionHandler` 拦截 Controller/Service 抛出的异常，统一转 Result。

已覆盖异常类型：
1）MethodArgumentNotValidException（参数校验失败）；
2）HttpMessageNotReadableException（请求体格式错误）；
3）DuplicateKeyException（唯一约束冲突）；
4）DataIntegrityViolationException（数据完整性异常）；
5）MultipartException（上传异常）；
6）IllegalArgumentException（非法参数）；
7）NoSuchElementException（资源不存在）；
8）WebClientResponseException（算法服务异常）；
9）Exception / RuntimeException（兜底异常）。

工程意义：
1）减少控制层 try-catch 重复；
2）避免堆栈信息直透前端；
3）前端能稳定根据 code 做提示。

第三章 config 包实现

----------------------------------------------------------------------
3.1 WebConfig：运行环境的总配置类
----------------------------------------------------------------------

WebConfig 实现了：
1）根路径重定向 `/ -> /api/health`；
2）CORS 跨域规则；
3）WebClient Bean 注入；
4）PasswordEncoder 注入；
5）AuthFilter 注册；
6）上传图片静态资源映射；
7）favicon 兜底处理。

其中与你项目最相关的是：
（1）WebClient Bean 设置了响应超时，AlgorithmClientService 直接复用；
（2）`/static/uploads/** -> file:./uploads/` 映射后，前端可直接显示上传图；
（3）AuthFilter 注册为 `/api/*`，保证业务接口都可拿到登录态上下文。

----------------------------------------------------------------------
3.2 AuthFilter：认证入口过滤器
----------------------------------------------------------------------

AuthFilter 是登录态解析入口，核心逻辑：
1）先判断白名单路径；
2）白名单直接放行；
3）非白名单读取 `X-Auth-Token`；
4）通过 tokenStore 查 userId；
5）把 userId 放进 request attribute (`currentUserId`)；
6）放行到后续 Controller。

白名单包含：
- /api/auth/login
- /api/auth/register
- /api/health

你文档里提到的重点是对的：这里使用 `request.setAttribute` 是为了在同一请求链路中传递“已解析身份”，避免控制层重复解析 Header。

注意：当前过滤器是“解析型”不是“强拦截型”，即 token 无效时不一定立即 401，而由业务层决定返回逻辑。这是当前项目的实现选择。

----------------------------------------------------------------------
3.3 AuthTokenStore：轻量会话映射
----------------------------------------------------------------------

AuthTokenStore 用 `ConcurrentHashMap<String, Long>` 保存 token 到 userId 的映射。

三个关键方法：
1）put(userId)：生成 UUID token 并保存；
2）getUserId(token)：按 token 查 userId；
3）remove(token)：登出时失效 token。

为什么用 ConcurrentHashMap：
1）线程安全，适合并发请求；
2）读写性能足够；
3）实现简单，适合课程项目。

局限也很明确：
1）重启丢会话；
2）多实例不共享；
3）无 TTL。
后续可升级 Redis 会话。

----------------------------------------------------------------------
3.4 InitDataRunner：启动初始化
----------------------------------------------------------------------

系统启动时检查 admin 是否存在，不存在则自动创建默认管理员。  
这个类的作用是保证首次部署可用，避免“系统启动后无法登录”的尴尬。

第四章 dto 包实现
======================================================================

dto 的作用是“定义接口协议”，不是数据库映射。

----------------------------------------------------------------------
4.1 认证相关 DTO
----------------------------------------------------------------------

1）LoginRequest：username/password，附参数校验；
2）RegisterRequest：username/password，附参数校验；
3）LoginResponse：token + user；
4）UserProfileDto：对外用户信息（不含 passwordHash）。

设计要点：前端需要什么字段，DTO 就暴露什么字段；敏感字段不对外。

----------------------------------------------------------------------
4.2 识别相关 DTO
----------------------------------------------------------------------

1）RecognitionResultDto：上传识别后直接返回给前端；
2）RecordListDto：历史记录列表；
3）RecordReportDto：单条记录报告；
4）IndividualListDto：个体列表；
5）IndividualReportDto：个体报告 + 图片时间序列。

DTO 设计体现了“页面导向”：列表页、详情页、报告弹窗的数据都在对应 DTO 中完成聚合。

----------------------------------------------------------------------
4.3 DTO 分层价值
----------------------------------------------------------------------

1）entity 改动不直接影响前端协议；
2）后端可做字段脱敏；
3）服务层可按页面场景拼装数据；
4）接口演进更稳。

======================================================================
第八章 service 包实现（业务核心）
======================================================================

service 是后端最关键层，承接业务编排与规则实现。

----------------------------------------------------------------------
8.1 AuthService
----------------------------------------------------------------------

1）login(username, password)
流程：
（1）findByUsername；
（2）BCrypt matches；
（3）tokenStore.put；
（4）组装 LoginResponse。

2）register(RegisterRequest)
流程：
（1）用户名查重；
（2）密码 encode；
（3）insert user；
（4）生成 token；
（5）返回 LoginResponse（注册即登录）。

3）logout(token)
调用 tokenStore.remove。

4）currentUser(userId)
判空 -> findById -> toProfile DTO。

----------------------------------------------------------------------
8.2 UserService
----------------------------------------------------------------------

主要实现：
1）getProfile；
2）updatePassword（校验旧密码 + 新密码加密更新）；
3）restoreData（业务恢复入口）。

你在总结里对 BCrypt 说明是正确方向，这里强调一点：系统只存 hash，不存明文，matches 时会自动处理盐值，这就是它安全性的核心。

----------------------------------------------------------------------
8.3 AlgorithmClientService
----------------------------------------------------------------------

这是 Java 对接 Python 的核心类，当前实现的真实协议是：
1）POST；
2）multipart/form-data；
3）字段名是 file；
4）响应 JSON 至少包含 identity_id（兼容 identityId）。

核心流程：
（1）校验文件非空；
（2）构建 multipart body（ByteArrayResource + 文件名）；
（3）webClient.post 调算法 URL；
（4）block(timeout) 获取响应；
（5）解析 identity_id；
（6）失败重试（最多 3 次，退避等待）；
（7）最终成功返回 AlgorithmResult，失败返回 null。

这里补充纠正一个常见误区：当前认证 token 不是放在 Authorization 头，而是 X-Auth-Token；算法调用是服务间调用，不依赖用户头。

----------------------------------------------------------------------
8.4 RecognitionService（主链路编排）
----------------------------------------------------------------------

submit(file, type, operatorUserId) 是最关键业务流程：

第一步：saveFile
（1）检查并创建上传目录；
（2）用 UUID 生成唯一文件名；
（3）保存文件并返回路径。

第二步：insert processing record
写 recognition_record，状态置 processing，记录操作者与类型。

第三步：call algorithm
调用 algorithmClient.recognize(file)。

第四步：分支处理
A 成功：
（1）findOrCreateIndividual 按 identity + speciesType 归并；
（2）更新记录为 done 并关联 individualId；
（3）插入 individual_image（含 shotTime、来源记录）；
（4）必要时更新个体封面；
（5）返回成功 DTO。

B 失败：
（1）更新记录 failed；
（2）返回失败 DTO。

这个流程是“可追踪识别系统”的关键：即便算法失败，也有失败记录可查询，不会出现“前端失败但后台无痕”的问题。

----------------------------------------------------------------------
8.5 RecognitionService 查询能力
----------------------------------------------------------------------

1）getResult(taskId)：任务结果查询；  
2）listRecords(...)：历史记录筛选，补 operatorName；  
3）getRecordReport(recordId)：单条报告；  
4）listIndividuals(speciesType)：个体列表；  
5）getIndividualReport(individualId)：个体详情（时间序列图片）。

这五类查询组合，实现了“任务维度 + 个体维度”的双视角数据展示。

第九章 数据库实现与业务关系
======================================================================

9.1 user 表
用户认证基础表，username 唯一约束保证注册冲突可控。

9.2 recognition_record 表
识别任务主表，承载状态流转、操作者、识别结果、关联个体。

9.3 individual 表
同一生物归并表，通过 algorithm_identity_id + species_type 区分个体。

9.4 individual_image 表
个体图片明细表，shot_time 支持时间域排序，recognition_record_id 支持来源追溯。

9.5 关系总结
1）user 1:n recognition_record；  
2）recognition_record n:1 individual（可空）；  
3）individual 1:n individual_image；  
4）individual_image 可溯源 recognition_record。

第十章 注册功能实现（融合后版本）
======================================================================

当前项目注册功能已完整落地：

1）DTO：新增 RegisterRequest（username/password + 参数校验）；  
2）Service：AuthService.register（查重 -> 加密 -> 插入 -> 发 token）；  
3）Controller：新增 POST /api/auth/register；  
4）Filter：白名单加入 /api/auth/register。

返回语义：
1）成功：Result.ok(LoginResponse)；  
2）用户名冲突：Result.fail(ResultCode.CONFLICT, "用户名已存在")；  
3）参数非法：由全局异常处理输出 BAD_REQUEST。

这使认证链路从“登录/登出”升级为“注册/登录/登出/当前用户”完整闭环。

第十一章 Java 对接 Python 算法的实现过程
======================================================================

11.1 协作边界
Java 负责上传流程编排、HTTP 调用、结果解析、落库；  
Python 负责模型推理并返回 identity_id。

11.2 Java 侧关键实现
AlgorithmClientService：
1）读取图片字节；
2）构建 multipart file 字段；
3）POST 到 algorithm.service.url；
4）解析 identity_id；
5）超时与重试。

11.3 Python 协作壳
`backend/algorithm-service` 提供：
1）main.py：固定 HTTP 入口；  
2）inference.py：算法同学只填 run_inference(image_bytes)；  
3）requirements.txt：依赖清单。

11.4 联调流程
1）算法服务启动；  
2）后端 URL 指向算法服务；  
3）前端上传测试；  
4）检查返回和数据库状态。

第十二章 可靠性、安全性与可扩展性
======================================================================

12.1 已实现的可靠性措施
